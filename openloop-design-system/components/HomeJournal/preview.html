How tool-using agents fail: a taxonomy of 312 runs

Abstract. We classified every failed run from six months of production traffic. More than half failed before any reasoning mattered: the model chose the right tool and passed it a malformed argument. We describe the categories, the heuristics that separate them, and guardrails that removed a third of failures without touching the model.

Boring infrastructure for fast-moving models

The model layer changes every month. The platform beneath it should not.

When a new model arrives, the temptation is to rebuild around it. We have done this twice, and both times the costly part was not the model. It was the assumptions that had quietly spread from the old model into queues, caches and retry logic.

The remedy is dull and effective. Treat every model call as an event in an append-only log, keep prompts and tool schemas versioned beside the code, and make the evaluation set the only authority on whether a change is an improvement.

Under this discipline a model swap becomes a configuration change with a measured outcome. A crashed run replays from its log and resumes. A regression is a failing test, not an anecdote from a customer.

None of this is novel. That is the argument. The interesting engineering lives in the models and the evaluations, and every hour spent on the platform should be an hour that the models never notice.
